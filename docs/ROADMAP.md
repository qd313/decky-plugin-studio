# Decky Plugin Studio — roadmap (deferred)



Star ratings follow bonsAI [roadmap](https://github.com/cantcurecancer/bonsAI) legend (effort/risk, 1 = lowest).



| Item | Stars | Status | Notes |

|------|-------|--------|-------|

| Native Steam Input / HID bridge in preview | ★★★★★★ | Deferred | W3C Gamepad only; see PREVIEW_LIMITATIONS |

| Gamescope / QAM compositing in preview | ★★★★★★ | Deferred | Requires CEF/chrome capture |

| Deck UI automation (`deck.openPlugin` hard) | ★★★★ | Deferred | v1 returns agent checklist only |

| Auto `.env` → `config.ts` on deploy | ★★★ | Plugin-specific | Use `.decky/preview.json` `preDeployCommand` |

| Pixel-perfect `@decky/ui` mocks | ★★★★ | Partial | v0.2 richer shims; on-device QA still required |

| Spam-left escape chain (plugin → plugin list → QAM → game) | ★★★★★ | Deferred | **Verified on hardware 2026-08-14:** D-pad left at the plugin's leftmost stop moves focus to Steam's own QAM icon rail, and further left presses do nothing — Steam consumes them. So the chain is not a gap to fill, it is a Steam behavior to override. Getting past the rail means patching Steam's QAM UI, not plugin code: fragile across Steam updates, and it changes behavior system-wide rather than only inside the plugin. A narrower version (left at the plugin edge pops back to the Decky plugin list) may be ★★★ if the press can be intercepted before Steam takes it — unverified. |

| **Pluckable studio** — adopt one piece without adopting all of it | ★★★ | Planned | Today Init Pack is all-or-nothing. | **Status bar is missing in VS Code** | ★ | Fixed 2026-08-26 | Reported 2026-08-26: the status bar shows in Cursor but not in VS Code. **Cause: the extension was not installed in VS Code at all.** `~/.vscode/extensions/` held 19 extensions and none was DPS; `~/.cursor/extensions/` had two (`0.1.2` and `0.3.6`). Cursor and VS Code keep separate extension directories, so a VSIX installed in one is invisible to the other. The status bar code was never at fault: [statusBar.ts](../extension/src/ui/statusBar.ts) calls `show()` unconditionally and `onStartupFinished` activation fires with or without a plugin workspace. **Resolved by building a fresh VSIX (`pnpm deploy:vscode`) and installing it** — `code --list-extensions` now reports `decky-plugin-studio.decky-plugin-studio-extension@0.3.6`, and the bundled MCP server carries the current deck tools (`deck_readPage`, `deck_walkTo`, `deck_runSequence`, `deck_waitFor`). **Two latent defects found while diagnosing were fixed at the same time**, because both produce this exact symptom and neither leaves a trace: (1) the item had no `id` or `name`, so a user who hid it had no findable entry in the status bar's right-click *Manage* menu — it looked gone forever; now `deckyPluginStudio.status` / "Decky Plugin Studio". (2) the text was one long item (`Decky v… | Preview ● | ● Tunnel | N ingest | ● Ollama | HW: …`) and VS Code **silently drops** right-aligned items that do not fit, with no overflow affordance — so a narrow window or a crowded bar made it vanish. Text is now `$(play) Decky ●●●` and every detail (plus `deckReachable`, which the bar never showed) moved to a markdown tooltip, which has no width limit. **Still open:** Cursor has 0.1.2 and 0.3.6 stacked — harmless (the highest version wins) but worth clearing so it is obvious which is live. |

| **Installed extension was inert — bundled MCP server could never start** | ★★ | Fixed 2026-08-26 | Found while chasing "the status bar says everything is offline". Three defects stacked into one misleading symptom. **(1) The VSIX never shipped the MCP server's dependencies.** [bundle-for-vsix.mjs](../extension/scripts/bundle-for-vsix.mjs) copied `mcp-server/dist` and nothing else — no `package.json`, no `node_modules` — while the preview-server got a full `npm install`. The server's first `import "pngjs"` threw `ERR_MODULE_NOT_FOUND` and the process died before reading a single request, so **every Studio tool was dead in any installed build, and always had been**. It only ever worked from a source checkout. Missing `package.json` also cost `"type": "module"`, leaving Node to guess ESM by sniffing syntax. Fixed by bundling the manifest and running `npm install --omit=dev`; VSIX grew 18.3 → 25.5 MB, nearly all of it `typescript`, which the lint rules genuinely need at runtime. **(2) The failure was silent.** `spawnMcpProcess()` was called with `.catch(() => {/* dev mode without built MCP */})`, and a dead server left `initialize` hanging for its full 120s timeout. Now the process `exit` and `error` events reject every in-flight request immediately, stderr is captured to a **Decky Plugin Studio** output channel, and `McpState.mcpHealth` distinguishes `starting` / `running` / `failed`. **(3) The status bar reported a dead server as a dead Deck.** Every signal it shows is read *from* the server, so when the server is down they are all false for the same uninformative reason — it rendered as "your Deck is offline" and sent the user to check their network. It now shows `$(warning) Decky (server failed)` on a warning background, and clicking it opens the log. **Guard added so this cannot ship again:** [smoke-mcp-bundle.mjs](../extension/scripts/smoke-mcp-bundle.mjs) starts the bundled server exactly as the installed extension does and fails the package step unless it answers `initialize`. A dependency check would have caught only this one omission; starting it catches the class. |

| **VS Code settings were read by nothing** | ★ | Fixed 2026-08-26 | `deckyPluginStudio.deckIp`, `.deckUser`, `.ingestPort`, `.previewHttpAllow` and `.localLoaderUnit` have been in the manifest since 0.1.0, and there was **not one `getConfiguration` call anywhere in the extension**. A user could type their Deck's IP into VS Code settings, see it saved, and get no connection and no complaint — the server only ever read `~/.config/decky-plugin-studio/deck.env`. A setting that does nothing is worse than no setting: it sends you looking at your network. `deckIp` / `deckUser` / `ingestPort` now reach the server as environment variables at spawn, and [config.ts](../mcp-server/src/config.ts) `readDeckEnv()` layers them over the file. **Blank counts as unset**, so the empty default cannot wipe out a working `deck.env`. Verified three ways: file only → reachable, override with a bogus IP → unreachable, blank override → still reachable. `previewHttpAllow` and `localLoaderUnit` are still unread — narrower, and neither has been reported. |

| **Status bar was a one-shot snapshot** | ★ | Fixed 2026-08-26 | `statusBar.refresh()` ran once at activation and there was no timer anywhere in the extension. Start a tunnel and the bar still said off; wake the Deck and it still said unreachable. The only cure was the refresh command, which you would only think to run if you already suspected the bar was lying. Now polls `deck_status` every 30s — a ping with a 1s deadline plus one local HTTP probe, cheap enough to repeat, slow enough not to spawn subprocesses in a tight loop. |

| **`deck_getEnv` hangs on an unreachable `DECK_IP`** | ★ | Open — found 2026-08-26 | [deckAutonomy.ts](../mcp-server/src/tools/deckAutonomy.ts) `getEnv()` calls `probeRemoteDeck()` whenever a non-local host is configured, and that SSH probe has no timeout. With a wrong IP the tool never returns — measured at >40s before the test gave up, against `pingDeck()`'s 1s deadline in the same call. Low impact today because the status bar polls `deck_status`, not `getEnv`. It matters the moment someone mistypes an IP and asks an agent what the environment looks like. Fix is a deadline on the probe, and reporting the timeout as a finding rather than hanging. Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 1 |

| **Deck automation killswitch** — stop everything, instantly, from anywhere | ★★ | Shipped 2026-08-27 | The rig presses real buttons on a real device. The firmware backstop (neutral-on-silence watchdog, 750 ms) covers the host dying; nothing covered a host that is alive, confident and wrong — which on 2026-08-26 left the ring on a game's **Play** button, one press from launching it, with no recourse but noticing and stopping by hand. **The latch is a FILE**, [`~/.config/decky-plugin-studio/automation-stop.json`]: there are always at least two server processes — the one the extension spawns and the one an agent spawns from `mcp.json` — they share no memory, and *the process a human can reach is not the one driving the Deck*. An in-memory flag would have stopped the wrong process. A file is also the only latch that survives a server restart. **Order was changed from the plan:** the latch is set FIRST, not fourth. Releasing the board first leaves a window where an in-flight run presses again while the release is still opening the serial port; the latch is one synchronous write, and everything after it happens with the rig already unable to press. Then release ([pad.py](../bridge/tools/pad.py) `release`), then tunnel teardown — CDP forwards and the ingest reverse tunnel, counted separately because one is the automation path and the other is only log traffic. Aborting in-flight runs needed no separate mechanism: `bridgeDisabled()` in [pressButton.ts](../mcp-server/src/deck/pressButton.ts) already gates every press, so it gates the latch too, and `runSequence` / `walkTo` / `openPlugin` check it at each loop top only so they can *report* a stop as a stop rather than as a cascade of failed presses. **Re-arming is deliberately not a tool.** It lives at `control/armAutomation`, which `handleMcp()` has no route to — verified against a real MCP session, which gets `Unknown method`. An agent that can clear its own killswitch does not have one. **Reachable four ways:** a dedicated status bar item (priority 1000, its own id/name, error background when stopped and warning background while a run is live), `Decky: Stop All Deck Automation`, <kbd>ctrl+alt+.</kbd>, and `pnpm stop` from a terminal for when nobody is in the IDE. The status bar item reads the latch file directly rather than asking the server, because a dead server must not be able to render a stopped rig as armed. The CLI script writes the latch with nothing but `fs`, so it works in a checkout that was never built. **Found and fixed alongside:** the VSIX never bundled `bridge/tools/`, so `findPadTool()` returned null in every installed extension — the killswitch could not have released the board there, and `deck_pressButton` / `deck_openPlugin` had never worked from a VSIX either. Now bundled, with a packaging check. |

| **One D-pad test, two runners — attach the preview controller to the device rig** | ★★★★ | Planned — requested 2026-08-27 | **The ask:** a focus/D-pad sequence should be written once and runnable in *both* places — against the in-IDE preview (fast, free, no hardware, runs in CI) and against a real Deck through the bridge (slow, truthful). Today they are two unrelated surfaces: `preview_runSequence` / `preview_injectFocusEvent` drive the W3C Gamepad mocks, `deck_runSequence` / `deck_walkTo` drive real HID through Steam Input, and a test written for one cannot run on the other. **What it is worth, stated honestly: a shared test *definition*, not a shared verdict.** The preview cannot answer Deck focus questions and must never look like it can — Steam's nav graph does not exist there (PREVIEW_LIMITATIONS; bonsAI findings-log P1-5). The win is that one file describes the walk, the preview run catches the cheap half early (a control that stopped rendering, a label that changed, a stop that left the DOM), and the device run stays the only thing that can say the ring moved. **Evidence from 2026-08-27, and it cuts both ways.** A bonsAI spoiler-fence bug was reproduced twice on device by `deck_runSequence` (`runs/SPOILER-REVEAL-BEFORE-fix.json`, `-AFTER-fix.json`): with a masked fence on screen — `Focusable`, `tabindex="0"`, in the scroll band — Down walked question → Helpful → Retry → … and never reached it. **A preview run would have reported that walk as fine**, because every element it looks for was present and correctly marked; what is broken is Steam's routing, which the preview does not have. So this feature must be built as *two runners over one definition*, with the preview result labelled as a smoke check and never merged into the device verdict — the moment a green preview can be mistaken for a green device row, it is worse than not having it. **Sequencing:** worth less than the three tool defects found the same day (below), which cost real time in a live run; worth more than any preview-fidelity work, because fidelity is the thing it explicitly refuses to promise. |

| **`deck_waitFor` reports satisfied/unsatisfied wrongly** | ★ | Open — found 2026-08-27 in a live run | Twice in one session the verdict contradicted the value. (1) An expression returning `null` came back `satisfied: true, polls: 1, waitedMs: 465` while the Ask it was waiting on was still streaming — the tool's own description says it "stops on the first **truthy** value", and `null` is not truthy. (2) Later, an expression returning a populated object came back `satisfied: false` after 60 polls, with `value: {done: true, fences: 1}` — the condition it was asked for, sitting in the result it called a timeout. **Why this one matters more than its star rating:** this tool is the reply-finished oracle for every Ask macro, and a wait that lies in *both* directions is the exact false-instrument class the rig was built to remove. Caught here only because the run cross-checked every wait against a direct `deck_readPage`; an unattended nightly would have recorded a reply as finished when it had not started. Fix the truthiness test and the `equals` comparison, and add a case for each direction. **Second session corroborates the false-negative half, 2026-08-27 later run:** twice more, `satisfied: false` after the full timeout with a truthy final `value` — once an object, once a plain boolean `true` — so "return only booleans" is not a workaround. (A late-finishing ~3-minute generation ending right at the deadline could explain any one occurrence, but not four across two sessions.) Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 2 |

| **`deck_runSequence` cannot start from an unowned ring** | ★ | Open — found 2026-08-27 | It reads focus before pressing and aborts with `"could not read focus before the run started, so nothing was pressed"` when nothing owns the ring. That is not an edge case: it is the state after **every** plugin open and after **every** finished Ask — confirmed on device the same day, and `deck_walkTo` already handles it with `acquireFocus`, which exists precisely because of it. So the sequence runner refuses in the situation its sibling was built to expect. Workaround is a bare `deck_pressButton` first, which wastes a press and puts the ring somewhere the caller did not choose. Give it the same `acquireFocus` option and default it on. Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 3 |

| **`deck_deploy` guesses the plugin directory and gets the case wrong** | ★ | Open — found 2026-08-27 | Failed with a bare `Error: Command failed: scp -r ... deck@…:~/homebrew/plugins/bonsai/dist` against a plugin installed at `~/homebrew/plugins/**bonsAI**/`. Two problems behind one unhelpful message: the target name is lower-cased rather than read from `plugin.json`'s `name`, and the installed directory is root-owned so a plain `scp` as `deck` could not have written it even with the right case. The error surfaces neither fact. Read the name from the manifest, and when the destination is not writable say so instead of echoing the failed command. Hit again in a second session the same day; the consumer's workaround is its own deploy script (bonsAI `build.ps1`), which uses a temp-dir upload plus an elevated move — the pattern this tool should adopt. | **The build never copies capture scripts into `dist`, so `deck_captureScreenshot` is dead from a source checkout** | ★ | Open — found 2026-08-27 | The tool errors with `Missing capture scripts: …/mcp-server/dist/scripts/deck/studio-capture-common.sh or studio-capture.sh`. Running the MCP server from the source tree is not an exotic setup — it is the configuration this repo's own `mcp.json` warning pushes consumers toward, since a version-pinned extension path goes stale on every release (the exact failure bonsAI hit on the 0.3.8 upgrade). Consequence for a live rig session: walks produce JSON evidence but no pixels — the single biggest evidence-quality gap in on-device QA today. Fix: copy `scripts/` into `dist` at build time, or fall back to resolving them from the source tree when `dist` lacks them. Same packaging-class defect as the VSIX misses above (MCP deps, `bridge/tools/`) — a smoke test that *calls* `deck_captureScreenshot` from a built tree would catch the class. Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 5 |

| **`deck_status` does not report bridge health, and the bridge is the thing that actually blocks sessions** | ★ | Open — requested 2026-08-27 | `deck_status` reports tunnel, ingest, Deck reachability and Ollama — everything except whether the ESP32 bridge can open its COM port. In a live session the board was unplugged; every press tool refused (correctly, loudly), but nothing surfaced it until the first press was attempted, and the session's working rule is now "send one harmless direction press as the first act of any device session" — a probe the status tool should own. Ask: try opening the configured port (or run `pad.py` in a status mode) and report `bridgeReady: true/false` plus the port name, so the physical-replug fix happens before a run starts rather than mid-run. Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 1 |

| **`deck_openPlugin` fails when the panel is already open** | ★ | Open — found 2026-08-27 | With the bonsAI panel already on screen and the ring inside it, the tool reported `walked 1 control(s) without finding "bonsAI"` and `ok: false` — it was looking for the plugin's entry in the Decky list while standing inside the plugin.
