| **Deck automation killswitch** — stop everything, instantly, from anywhere | ★★ | Shipped 2026-08-27 | The rig presses real buttons on a real device. The firmware backstop (neutral-on-silence watchdog, 750 ms) covers the host dying; nothing covered a host that is alive, confident and wrong — which on 2026-08-26 left the ring on a game's **Play** button, one press from launching it, with no recourse but noticing and stopping by hand. **The latch is a FILE**, [`~/.config/decky-plugin-studio/automation-stop.json`]: there are always at least two server processes — the one the extension spawns and the one an agent spawns from `mcp.json` — they share no memory, and *the process a human can reach is not the one driving the Deck*. An in-memory flag would have stopped the wrong process. A file is also the only latch that survives a server restart. **Order was changed from the plan:** the latch is set FIRST, not fourth. Releasing the board first leaves a window where an in-flight run presses again while the release is still opening the serial port; the latch is one synchronous write, and everything after it happens with the rig already unable to press. Then release ([pad.py](../bridge/tools/pad.py) `release`), then tunnel teardown — CDP forwards and the ingest reverse tunnel, counted separately because one is the automation path and the other is only log traffic. Aborting in-flight runs needed no separate mechanism: `bridgeDisabled()` in [pressButton.ts](../mcp-server/src/deck/pressButton.ts) already gates every press, so it gates the latch too, and `runSequence` / `walkTo` / `openPlugin` check it at each loop top only so they can *report* a stop as a stop rather than as a cascade of failed presses. **Re-arming is deliberately not a tool.** It lives at `control/armAutomation`, which `handleMcp()` has no route to — verified against a real MCP session, which gets `Unknown method`. An agent that can clear its own killswitch does not have one. **Reachable four ways:** a dedicated status bar item (priority 1000, its own id/name, error background when stopped and warning background while a run is live), `Decky: Stop All Deck Automation`, <kbd>ctrl+alt+.</kbd>, and `pnpm stop` from a terminal for when nobody is in the IDE. The status bar item reads the latch file directly rather than asking the server, because a dead server must not be able to render a stopped rig as armed. The CLI script writes the latch with nothing but `fs`, so it works in a checkout that was never built. **Found and fixed alongside:** the VSIX never bundled `bridge/tools/`, so `findPadTool()` returned null in every installed extension — the killswitch could not have released the board there, and `deck_pressButton` / `deck_openPlugin` had never worked from a VSIX either. | **`deck_waitFor` reports satisfied/unsatisfied wrongly** | ★ | Fixed 2026-08-27 | Twice in one session the verdict contradicted the value. (1) An expression returning `null` came back `satisfied: true, polls: 1, waitedMs: 465` while the Ask it was waiting on was still streaming — the tool's own description says it "stops on the first **truthy** value", and `null` is not truthy. Caught here only because the run cross-checked every wait against a direct `deck_readPage`; an unattended nightly would have recorded a reply as finished when it had not started. Fix the truthiness test and the `equals` comparison, and add a case for each direction. **Second session corroborates the false-negative half, 2026-08-27 later run:** twice more, `satisfied: false` after the full timeout with a truthy final `value` — once an object, once a plain boolean `true` — so "return only booleans" is not a workaround. (A late-finishing ~3-minute generation ending right at the deadline could explain any one occurrence, but not four across two sessions.) Plan: [05-parallel-bugfix-session.md](planning/05-parallel-bugfix-session.md) lane 2 **Fixed, and the root cause was neither the truthiness test nor the CDP unwrapping.** `waitFor()` decided whether the caller wanted exact-match mode with `hasOwnProperty(opts, "equals")` -- a test for the KEY, not the value. The existing tests never caught it because they call `waitFor()` directly and simply omit the key, never reproducing the shape the handler always produces. **Verified on the rig 2026-08-27:** `null` -> not satisfied after 9 polls; `true` and `{done:true,fences:1}` -> satisfied on poll 1 in ~340ms; `false` -> not satisfied. |

| **`bridgeReady` and `fidelity: "steam-routed"` both report success down a dead path** | ★★★ | Open -- found 2026-08-27 in the on-device pass | **The most serious thing the pass found, and it is a false instrument rather than a missing one.** With the bridge board still on COM7 but its **USB HID lead to the Deck unplugged**, every layer reported success and nothing happened: `deck_status` returned `bridgeReady: true`, `deck_pressButton` returned `ok: true` with `fidelity: "steam-routed"` and a firmware ack of `{"ok":true,"t":"press","dirs":2}`, and a `deck_readFocus` either side of the press showed the ring on `"What's New"` **before and after**.
